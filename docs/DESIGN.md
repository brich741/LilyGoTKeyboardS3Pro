# Design notes and rationale

Read this before changing the firmware, so past decisions and dead ends are not re-derived.
Companion docs: [CONFIG.md](CONFIG.md) (config/API contract), [CONTEXT.md](CONTEXT.md) (vocabulary),
[STM32_UPDATE.md](STM32_UPDATE.md) (flashing the co-processor), [../README.md](../README.md) (build/use).

Status snapshot: 2026-10-15. See "Open items" at the end for what is unfinished.

## 1. What this is
A USB macro keyboard for the LilyGo **T-Keyboard S3 Pro** that the owner configures **from a phone, without recompiling**.
Original requirements (the owner's words, condensed):
- Plugs into a PC as a USB keyboard; used to speed up Claude Code in VS Code (the extension panel, Windows).
- The device hosts a Wi-Fi AP; a phone browser edits everything live. No reflashing for config changes.
- 4 screen keys: upload an icon per key/state; each key has **single, double, hold** gestures, each sending key
  combos (Win+D etc.). Hold has a start action and an end action (push-to-talk: green mic while held, red when released).
- RGB strip: lights above the pressed key in a configurable colour; animations nice to have.
- Rotary encoder with push: turning cycles **pages** (sets of 4 key configs); push is a 5th button.
- C/C++ with PlatformIO.

## 2. Architecture

```
 phone browser ──Wi-Fi AP──► WebServer (core 0 task "web")  ◄── REST (docs/CONFIG.md) ── data/www SPA (plain JS)
                                   │ cfgMtx                                   ▲ icons: browser converts to RGB565
                                   ▼
   app::cfg (core::Config) ◄── main loop (core 1) ── GestureEngine x5 ── actions queue ──► worker task ──► USB HID
        │                          │  KeyVisual x4                              (per-key StepRunner,
        │                          ▼                                             shared HID key refcount)
        │                    screens (4x GC9107)   ledstrip task (core 0) ──► STM32 over I2C (hwMtx)
        ▼
   LittleFS: /config.json, /icons/<id>.565, /www/*
```

Layers (`firmware/`):
- `lib/core/` — **hardware independent**, unit-tested on the host: `config` (model, parse/validate, serialize, defaults),
  `gesture` (single/double/hold state machine + debounce), `runner` (Step lists -> HID calls, refcounted held keys,
  cooperative abort), `visual` (per-key icon/LED look over time), `leds` (effects, zone overlay, grouping into STM32
  paint ops), `keymap` (key/mod/media names <-> HID usages).
- `src/` — thin device layer: `main` (loop/orchestration), `actions` (USB + worker task), `screens`, `ledstrip`,
  `net` (AP, captive portal, REST), `storage` (LittleFS), `debuglog` (USB-CDC console).
- `data/www/` — the phone UI (one `app.js`, `style.css`, `index.html`), `data/icons/` starter icons (generated by
  `tools/make_icons.py`), mock mode via `?mock` for hardware-free UI work.
- `diag/` — one-off diagnostic sketches (see section 7); `test/test_core/` — Unity tests.

### Threads and locks
- Tasks: Arduino `loop` (core 1), `actions` worker (core 1), `leds` (core 0), `web` (core 0).
- `cfgMtx` guards `app::cfg`, counters. `hwMtx` guards **all** I2C/SPI traffic (displays, LEDs, key reads) because the
  display chip-selects are multiplexed over the same I2C bus. **Lock order: cfgMtx before hwMtx; never take cfgMtx while
  holding hwMtx.** (An independent review found no violations.)
- Config snapshots for saving are taken under `cfgMtx` together with a sequence number (`app::saveSeq`);
  `storage::save` is serialized and ignores a stale snapshot (so a slow debounced save can't overwrite a newer web PUT).
- Cross-task requests use counters/atomics (`generation`, `redrawGeneration`, `requestedPage` exchanged atomically).

## 3. Behaviour decisions (and why)
| Decision | Why |
|---|---|
| Single press waits for the double-press window **only if** that key has a double action | no added latency on keys that don't use double |
| A key without a `hold` action treats a long press as an ordinary single press | no lost presses |
| Hold has `start` and `end` step lists; anything still held after `end` is auto-released | push-to-talk is "key down on hold, up on release"; no stuck keys |
| Each key has its own `StepRunner`; a shared HID layer refcounts usages | two keys can both hold Ctrl; one key's release can't free another's keys |
| `releaseAll()` bumps an abort generation: running job aborts, queued jobs are dropped; queue capped at 16 | page switch / USB suspend must never leave keys held behind a 160 s delay chain |
| Page switch: release everything first, then run the old page's hold-end steps | clean state, end sequences still fire |
| Encoder push is a 5th input (single/double only). A 3 s hold is **reserved** and shows Wi-Fi SSID/password | recovery/convenience; the hold gesture is dropped from encoder config on parse |
| Encoder rotation = page switch (wraps), page name banner for 1 s, last page remembered (debounced save) | requested behaviour |
| Info screen closes only after the opening press is released | otherwise it flashed for one frame |
| Wi-Fi is **off at power-up** (`settings.wifiAtBoot`, default false). Wi-Fi screen (3 s knob hold) shows state, network name, password, address, client count; **knob push switches Wi-Fi for this session** (not persisted); any key or turning closes | the AP is only exposed when needed; control and visibility on the pad itself, no phone needed |
| Wi-Fi on/off is applied by the **web task** (`net::requestWifi`), which owns the WebServer/DNS objects; the server socket is created at the first enable | avoids touching the stack from two tasks; the listening socket needs the TCP/IP stack |
| Holding the knob at power-up resets SSID/password **and starts Wi-Fi for that session** | recovery if the credentials are lost |
| The phone UI has only a "start Wi-Fi at power-up" checkbox, no live toggle | switching Wi-Fi off from the phone would cut its own connection |
| Phone UI never "records" keys: modifier chips + key picker | phones have no physical keyboard |

## 4. Hardware facts (verified unless marked)
- ESP32-S3, 16 MB flash. Four GC9107 128x128 screens on one SPI bus (MOSI 40, SCLK 41, DC 39, RST 38, BL 1).
  **Screen chip-selects, the 5 keys and the 14 WS2812C LEDs are on an STM32G030F6P6** at I2C addr `0x01`
  (SDA 42, SCL 2, keep **400 kHz**; 1 MHz corrupts CS writes). Draw **one screen at a time** (never SCREEN_ALL).
- Encoder A/B are plain ESP32 GPIOs (4, 5). The encoder **push is KEY5** on the STM32 (index 4).
- LEDs (1-based): key pairs **1-2, 4-5, 7-8, 10-11**, encoder 13-14, gap LEDs 3, 6, 9, 12 (from LilyGo's STM32 sample).
  Default zones in config are these pairs.
- STM32 firmware behaviour (from LilyGo's STM32 repo, branch `stm32cubeg0-firmware-package_V1.6.2`):
  - Commands are queued **one I2C transaction late**; our 2 ms key polling flushes the queue. Version reads (`0x10`) return stale data.
  - LED registers: `0x03` mode (2 = free), `0x04` brightness, `0x05/0x06` hue high/low, `0x07` saturation, `0x08/0x09` select + flags.
    A *select* write **paints those LEDs with the current hue/sat/brightness registers into a persistent framebuffer**;
    *clear* wipes the **whole** buffer (and shows); *show* latches. So: paint every colour group, then **show once**; never clear between groups
    (that was a real bug: red zone erased, flickering intermediate frames).
  - **Factory firmware V1 has a hue bug** (LilyGo issue #7): hue is OR-ed into the old value so it can never be set; hue values
    above 359 render magenta-pink. Brightness and saturation work. Fixed in V2 (hex in LilyGo's repo, address 0x01).
    We proved it with LilyGo's stock `RGB.ino`, register sweeps, and Arduino core 3.x **and** 2.0.14 (core version is not the cause).
  - SWD connector X1 on the back of the keyboard PCB: pins `1 GND, 2 +3.3V, 3 SWCLK, 4 SWDIO`; UART X2: `RX, TX, +3.3V, GND`.
    SWCLK shares the BOOT0 pin. See STM32_UPDATE.md. (Connector looks like 1.0 mm JST-SH; schematic part `AFC10-S04PCA-00`.)

## 5. LED model in this firmware
`composeLeds` = page effect (off/solid/breathe/rainbow/chase/sparkle) + per-key zone overrides (a key's current look colour paints only its
zone). `planPaint` groups changed LEDs by quantized HSV into few paint ops; the LED task paints groups then shows once, at ~25 fps.
`settings.ledHue` (default **true**): real hues. `false` = legacy white/pink mode for pads still on the factory STM32 firmware
(hue forced to 0, `rainbow` becomes a rotating white<->pink saturation wave). Switch via web UI Settings or console `ledhue 0|1`.

### Captive portal (auto-open the settings page)
Goal: joining `ClaudePad` should take the user to the UI without typing a URL. How it works (`net.cpp`):
- `WiFi.softAPConfig(ip, gw, mask, dhcpStart, dns = ip)`: the **last argument is essential**. The core only makes the AP's DHCP offer itself as the DNS server
  when a DNS address is passed; without it phones keep their own DNS and our wildcard `DNSServer` (every name -> 192.168.4.1) never sees a lookup.
- `WiFi.AP.enableDhcpCaptivePortal()` adds DHCP option 114 (RFC 8910) so Android 11+/iOS 14+ show the sign-in prompt immediately (`captiveDhcp=1` in the `wifi` console command).
- The OS connectivity-check URLs (`/generate_204`, `/hotspot-detect.html`, `/connecttest.txt`, `/ncsi.txt`, ...) and every unknown path answer **302 -> http://192.168.4.1/**,
  which is what makes the OS show "Sign in to network". `/` serves the UI for any Host header, so typing any `http://name` also works.
- Limits: HTTPS URLs cannot be redirected (browser security); captive-portal mini-browsers (Android sign-in sheet, iOS) often can't open file pickers or
  download files, so icon upload and export should be done from the normal browser at http://192.168.4.1. Not yet verified end to end on a real phone.

## 6. USB / Windows lessons
- `ARDUINO_USB_MODE=0` (TinyUSB) with **`ARDUINO_USB_CDC_ON_BOOT=0`**. With CDC-on-boot the core calls `USB.begin()` before `setup()`, so the HID
  interfaces registered later never enumerate (the pad showed only a serial port). We register HID + our own `USBCDC` console, then `USB.begin()`.
- Custom **VID:PID 303A:4B50**, serial `CLAUDEPAD-0001`: with the board default 303A:1001 Windows bound Espressif's JTAG/serial driver to
  interface 0 (the HID interface) and the keyboard showed "Error".
- **Serial gotcha:** opening/closing the pad's COM port from a terminal toggles DTR/RTS and can drop the ESP32 into ROM **download mode**
  (it then enumerates as "USB JTAG/serial debug unit", screens dark). Recover with
  `python ~/.platformio/packages/tool-esptoolpy/esptool.py --chip esp32s3 --port COMx --after hard-reset chip-id` or replug.
- Typed text assumes a **US layout, ASCII only**. Key combos use HID usages and work on any layout.

## 7. Toolchain gotchas
- PlatformIO Core must be **>= 6.2** (pioarduino platform requirement); `pio upgrade` was not enough here, `pip install -U platformio` was.
- Platform: pioarduino stable (Arduino-ESP32 3.3.x). `lib_ldf_mode = deep+` **plus** explicit `-I` for the framework `FS` and `Network` libraries
  (the library finder skips conditional includes, so USB/WiFi/LittleFS failed to compile otherwise).
- Partition `spiffs` (type spiffs) must keep that **name**: Arduino `LittleFS.begin()` mounts label `spiffs`. 3 MB app + ~12.9 MB filesystem.
- **`pio run -t uploadfs` erases the filesystem, including saved config and uploaded icons.** Export a backup from the UI first.
  Starter icons come back with it (they live in `data/icons`).
- Run PlatformIO from PowerShell if Git Bash prints "MSys/Mingw is not supported".
- No host C++ compiler here: `python tools/host_tests.py` bootstraps zig (venv in `.hosttest/`) and runs the Unity tests. `pio test -e native` works
  only if gcc/clang is installed.
- Diagnostic envs in `platformio.ini` (flash `esp32s3` again afterwards): `rgbdemo` (LilyGo's stock RGB example), `ledexamples` (their example colour
  calls), `rgbcycle` (user's R/G/B test), `rgbdemo_core2` / `rgbcycle_core2` (same on Arduino core 2.0.14).
- Writing patch scripts: never embed a literal newline inside a C string via a shell heredoc (it broke the build twice); use real files.

## 8. Debug console (USB-CDC, any baud; needs DTR; see serial gotcha)
`help`, `status`, `wifi` (state) / `wifi 0|1` (switch for this session), `dumpconfig`, `type <text>`, `tap <key> [mods]`, `ledhue 0|1`, `ledpause 0|1`, `led h s v mask`, `ledraw ...`, `ledclear`,
`ledtest`, `ledprobe`, `huesweep` (labelled on the screens; they block the main loop ~30-45 s), `wipe`, `reset`.

## 9. Testing
- Host: `python tools/host_tests.py` (28 tests: keymap, gestures incl. debounce/double/hold, runner refcounts/abort, config round trip/validation,
  visuals, LED effects/grouping/hue modes). Keep `lib/core` free of Arduino headers so it stays testable.
- Web UI without hardware: serve `firmware/data/www` and open `index.html?mock`.
- On device checklist: icons on 4 screens, each key's single/double/hold reach the PC, push-to-talk green/red, encoder pages wrap, no stuck keys after
  page switch/unplug, config survives reboot, Wi-Fi AP visible, UI loads on a phone, LED zones calibrate, colours (after STM32 update).

## 11. Things already tried (don't repeat)
- Setting LED hue via any register value, ordering, pacing, `setLeds()` verbatim, stock LilyGo examples, Arduino core 2.0.14: **no effect on the factory STM32 firmware**.
- Reflashing the STM32 from the ESP32 over I2C: deliberately **not** attempted (a failed flash could disable keys, LEDs and screens). Use SWD.
- A mono (white/pink) LED fallback exists (`ledHue=false`) and works on the old STM32 firmware.
